# Catatan Keputusan Data: SiLapor Kampus

Persona acuan tetap Dina (NF-01: waktu hanya beberapa menit di sela kuliah; F-03: mengecek status beberapa kali per minggu).

| Keputusan | Pilihan Anda | Alasan (merujuk kebutuhan) |
|:----------|:-------------|:---------------------------|
| Field model | Delapan field: `id`, `kategori`, `lokasi`, `deskripsi`, `tanggal`, `status`, `fotoTerlampir`, `catatanPenanganan`. `judul` dihitung dari `kategori` dan `lokasi`, tidak disimpan. Tidak ada field identitas pelapor. | Tiap field ditelusuri ke F-01, F-02, F-03, atau F-06 pada `model-data.md`. Tidak menyimpan pelapor sesuai NF-03. `judul` turunan agar tidak bisa berbeda dari field asalnya. |
| Kunci data (`id`) | `String` dari `DateTime.now().millisecondsSinceEpoch` saat laporan dibuat. Update memakai `indexWhere((l) => l.id == ...)`, Delete memakai `removeWhere((l) => l.id == ...)`. | Dina bisa membatalkan (F-08) atau petugas mengubah status (F-06) pada laporan yang posisinya sudah bergeser karena pencarian atau laporan baru yang disisipkan di atas. Index berubah, id tidak. |
| Operasi CRUD per kebutuhan | Create: F-01, F-02. Read: F-03, F-04, F-07. Update: F-06 (simulasi). Delete: F-08. F-05 dan F-09 tidak dibuat. | F-01, F-03, dan F-04 adalah Must yang berjalan di sisi Dina, sehingga tuntas dengan CRUD lokal. F-05 dan F-09 adalah layar petugas yang butuh data bersama, jadi dicatat sebagai kebutuhan backend. |
| Update lewat simulasi petugas | Tombol "Ubah status (simulasi petugas)" pada detail. Status selain Menunggu wajib disertai catatan penanganan. | F-06 adalah Must dan harus ditunjukkan sebagai Update yang berjalan. Pada satu ponsel hanya bisa disimulasikan, jadi namanya dibuat jujur. Catatan wajib karena F-06 menyebut status beserta catatan penanganan. |
| Delete dengan konfirmasi | Tombol "Batalkan laporan" hanya muncul pada status Menunggu, dan membuka `AlertDialog` sebelum data dihapus. | F-08 hanya berlaku untuk laporan Menunggu. Menghapus laporan yang sudah diproses menghilangkan jejak penanganan. Dialog mencegah hapus tak sengaja karena tombol berada dekat tombol Kembali. |
| Letak state | `List<Laporan>` hanya ada pada `_HalamanUtamaState`. Form dan detail tidak mengubah daftar. Form mengembalikan `Laporan` baru lewat `Navigator.pop`, detail mengembalikan `HasilDetail`. | Satu pemilik data menjaga tampilan selalu sinkron. Bila form dan detail memegang salinan sendiri, layar bisa menampilkan data berbeda (gejala pada pemantik Pertemuan 7). Setiap perubahan terjadi di satu tempat dan dibungkus `setState`. |
| Tipe `tanggal` | `String` berformat `15 Okt 2026`, dibuat dari `DateTime.now()` tanpa package. | Hanya untuk tampilan seperti pada wireframe Tugas 5. Konsekuensinya urutan terbaru (F-05) bergantung pada penyisipan di indeks 0, bukan pada nilai tanggal. Saat data pindah ke server, tipe diganti `DateTime`. |
| Keputusan persistensi | Tidak diterapkan. Data disimpan in-memory dan kembali ke data contoh saat aplikasi dimulai ulang. `shared_preferences` tidak dipakai. | Berkas harus dapat berjalan di DartPad tanpa package. Konsekuensi yang diketahui: F-03 belum sepenuhnya terpenuhi karena Dina mengecek status beberapa kali per minggu, sedangkan laporannya hilang setiap aplikasi ditutup. Persistensi dan backend (Pertemuan 9 dan 10) menutup celah ini. |
